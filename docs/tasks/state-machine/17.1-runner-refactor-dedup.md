# Task 17.1 — StateMachineRunner Refactor — Eliminate run/resume Duplication

> **Phase**: 1 (Core Engine — maintenance)
> **Depends on**: Tasks 09–17 (all core engine tasks complete, 330 tests green)
> **Blocks**: Phase 2 (REST API) — cleaner runner makes API wiring easier

---

## Objective

Refactor `StateMachineRunner.ts` (currently 2,479 lines) to eliminate the massive code duplication between `run()` and `resume()`. The `resume()` method currently duplicates nearly the entire state loop from `run()` — including `persistError`, `executeAction`, `runPreamble`, the full `child_machine` / `parallel_children` / `action` branching, the terminal state resolution, and the `Effect.onInterrupt` finalizer. This means any bug fix to the state loop must be applied in **two places**, and the two copies can silently drift.

**This is a pure refactor — no behavior changes.** All 330 existing tests must continue to pass without modification.

### What differs between `run()` and `resume()`

Only the **setup phase** before the state loop differs:

| Concern                 | `run()`                          | `resume()`                                                 |
| ----------------------- | -------------------------------- | ---------------------------------------------------------- |
| Definition source       | Passed as argument               | Loaded from store by `instance.definitionId`               |
| Input source            | Passed as argument               | Loaded from `instance.input`                               |
| Initial `currentState`  | `definition.initialState`        | `instance.currentState` (persisted)                        |
| Initial `stateData`     | `input`                          | `instance.stateData` (persisted)                           |
| Initial `history`       | `[]`                             | `[...instance.history]` (persisted)                        |
| Initial `logs`          | `[]`                             | `[...instance.logs]` (persisted)                           |
| Instance creation       | `store.saveInstance(...)`        | Already exists — `store.updateInstance(status: 'running')` |
| Validation              | Definition + input schema        | Definition + version match                                 |
| Depth check             | `opts.depth > MAX_MACHINE_DEPTH` | N/A (depth is a fresh-run concern)                         |
| Pre-loop child handling | N/A                              | Resume suspended children first                            |
| `parentContext`         | From `opts`                      | Reconstructed from `instance.parentInstanceId` + history   |
| `machineInput`          | `input` argument                 | `instance.input`                                           |

Once the state loop starts, the logic is **identical**: acquire semaphore, run preamble, branch by state type, execute action, validate transition, run middleware, persist checkpoint, advance state, resolve terminal.

### 4. Extract the state loop as a shared function

This is the main extraction. The `while` loop with its three branches (`child_machine`, `parallel_children`, `action`) becomes a single function:

```typescript
const executeStateLoop = (
  loopState: LoopState,
  runner: StateMachineRunner, // for recursive child spawning
  opts?: { timeoutMs?: number }, // machine-level timeout
) =>
  Effect.gen(function* () {
    while (loopState.definition.states[loopState.currentState].type !== 'terminal') {
      const stateDef = loopState.definition.states[loopState.currentState];

      if (stateDef.type === 'child_machine') {
        yield* executeChildMachineState(loopState, runner, opts);
      } else if (stateDef.type === 'parallel_children') {
        yield* executeParallelChildrenState(loopState, runner, opts);
      } else {
        yield* executeActionState(loopState);
      }

      if (loopState.errorResult) return;
    }
  });
```

Each state-type branch can optionally be its own function (`executeChildMachineState`, `executeParallelChildrenState`, `executeActionState`) if the branches are large enough to warrant it.

### 9. Handle the resume-specific child_machine pre-check

The resume path has one piece of logic that doesn't exist in `run()`: before entering the state loop, it checks whether an already-completed child's result should be fed into `stateData`. This logic currently lives inside resume's state loop as a special case at the top of the `child_machine` and `parallel_children` branches.

**Approach:** Keep this as a pre-loop step in `resume()` only. Before calling `executeStateLoop`, if `loopState.currentState` is a `child_machine` or `parallel_children` state and the child(ren) have already completed, set `loopState.stateData` to the child result(s) and skip to the post-child action. This can be a separate `handleResumedChildState(loopState)` helper.

Alternatively, integrate the "check if child already completed" logic into `executeChildMachineState` / `executeParallelChildrenState` — since a fresh `run()` would never encounter an already-completed child, the check is effectively a no-op for `run()` and only activates on resume. This is simpler and avoids the resume-specific pre-check entirely.
